# Contributing

1. Read the architecture, governance, and security policy.
2. Check existing issues, specifications, and ADRs before proposing a new abstraction.
3. For non-trivial work, open an issue describing problem, user, constraints, acceptance criteria, and security/privacy impact.
4. Use a focused branch and pull request; explain behavior, compatibility impact, tests, and documentation updates.
5. Add or update tests for changed behavior. Interface/schema changes require compatibility fixtures.
6. Update the owning repository's manifest when purpose, interfaces, dependencies, maturity, license, or release state changes.
7. Do not add secrets, personal data, unlicensed datasets, or private operational material.
8. Do not claim a feature is implemented without reproducible evidence.

Prefer existing standards and interoperable formats. New protocols and schemas require an ADR and conformance examples.
